# SVY-21326 — MCP server

Where the case stands, 2026-08-27.

---

## What was asked

> A plugin, like RestWS, that quickly creates a client from a pool and runs a function
> in it. Those functions are scope functions annotated `@Tool`. At startup it knows
> which solution is the MCP solution and scans it for tool definitions, exposing them
> at `/mcp`. Authentication is needed, so tool definitions carry an extra `userToken`
> parameter that the AI fills with the token of the user the agent acts on behalf of,
> so we can auto-login through Servoy Cloud and set the tenant.

## What was decided

Six decisions changed the shape of the case. All but the last came out of the standup
on 2026-08-25.

**It lives in core, not in a plugin.** Reaching a solution's own logic needs the
application server itself, so it runs in the application server's own process and starts and
stops with it, roughly like a batch processor. It sits in a bundle of its own, `servoy_mcp`,
which `j2db_server` uses - see below for why it is not simply part of `j2db_server`.

**A solution declares itself by its type.** A new solution type, `MCP Service`, marks
a solution as reachable over MCP. There is no configuration at all: the solution is
named in the URL, `/servoy-service/mcp/<solution>`, and one server hosts as many as it
likes. `rest_ws` works the same way.

**Tool parameters are `String`, `Number` or `JSON`. Nothing else.** A tool declaring
anything else is not published, and the log says why.

**No limits are imposed by us.** The client pool is unlimited. How many concurrent
calls a deployment runs, and what that costs in licences, is the deployment's
business.

**The protocol is the official MCP SDK's** — the same one `servoy-developer-mcp` runs.

**We do not authenticate. The solution does.** The token is never read, decoded or
verified by the server; it is passed through untouched to the solution's authenticator
module, which answers who the bearer is, what they may do and which tenant they are in.
This came out of the standup: *"you give it to the authenticator module. That
authenticator module says, I'm logging in as this user with these permissions, and this
is the tenant... So there is no authentication code in your thing."* It is what lets a
deployment mint tokens in Servoy Cloud, or use an external identity provider, or keep a
table of API keys, without any of it being our concern.

**The token travels in the `Authorization` header**, not as a tool argument. That keeps
it out of the schemas the agent sees and out of whatever the agent logs.

## What is implemented

Thirteen classes in `com.servoy.mcp`, in a bundle of their own, plus a solution type and one
line of registration. 120 tests, all passing.

**Discovery.** Every scope of the solution is walked, and any function whose
documentation block carries `@Tool` becomes a tool. The description and the parameters
come out of the JSDoc. Reaching the solution model from the server goes through
`ClientPluginAccessProvider → IApplication → FlattenedSolution`, which is the route
`FunctionDefinition.exists()` uses.

**Schema.** `@param` tags become a JSON Schema. Optional parameters, written
`@param {String} [name]`, are left out of `required`. An unsupported type takes the
whole tool out of the list, with an error in the log.

**Protocol.** The SDK's stateless HTTP transport plus a sync server, one per solution,
built on first request. Tools are registered at build time from the scan.

**Execution.** A client is borrowed from a pool keyed on solution, user and tenants -
so a client can never be handed to a different user - the identity is applied to the
session, the scope function runs, the client goes back.

**Authentication.** The bearer is handed to the solution's authenticator module through
`IApplicationServer.login` with **no client id**. That detail is load-bearing: on that
path, and only on that path, the server runs the authenticator in a throw-away client
and returns the tenant alongside the user (`getRawTenantValue()`, added by SVY-21382).
Passing a client id would apply the identity to that client and return nothing - no use
here, because the tenant has to be known *before* a client is borrowed, being part of
the pool key. The identity is then applied with `setUserUid`, `setUserName`,
`setUserGroups` and `setTenantValue`, mirroring `NGClientWebsocketSession.setUserId()`.

**Staying current.** A solution is scanned once and its tools registered when its server is
built, so something has to say when that stopped being true. Two things do. An import - the
way a solution changes under a running server - calls `McpRuntime.invalidateAll()` where it
already flushes the repository. In the developer, an `IPersistChangeListener` in
`com.servoy.eclipse.core` does the same whenever a script method is saved.

Dropping our own cache turned out not to be enough. The scan reads the solution model
through a client, and the repository hands every new client the same loaded solution until
that copy is flushed - so even a brand new client saw the old version. Invalidating now
flushes the solution's root object, and its modules' too, since a module is cached
separately but edited like any other part of the solution. Named root objects rather than
`flushAllCachedData()`: this runs on every save in the developer, and emptying the whole
repository each time would be felt across the IDE.

### What is covered

The tests are the record of what works; the table below is what they assert.

| | |
|---|---|
| discovery | the marked functions become tools, and an unsupported-type one does not |
| descriptions | what the agent is told about a tool comes out of the JSDoc |
| schemas | String, Number and JSON map to JSON Schema; anything else is refused |
| no token | refused before an authenticator is even looked for |
| unknown token | refused, with the authenticator's own message |
| the token itself | reaches the authenticator untouched, with no client id |
| two users | `alice`/`alice-uid` and `bob`/`bob-uid` end up on their own sessions |
| **tenant isolation** | the tenant from the authenticator is what is set on the client |
| pooled client reuse | the same user gets their client back; another user never does |
| **invalidation** | a changed solution loses its server and its pooled clients, others keep theirs |
| results | `42`, not `42.0`; a JSON return arrives as an object; null and arrays are rendered |
| failure paths | an invalid client is not handed out again; an unknown solution invalidates harmlessly |

The wiring on top of that - the endpoint being served, the `Accept` header the SDK insists on,
a tool saved in the developer appearing without a restart - was exercised by hand against
`mcp_sample` in a running developer, and by an earlier round of integration tests since removed
(see below).

Two things the testing itself taught, neither of them a fault in this code:

1. `security.login()` refuses any permission that does not exist as a group in the
   resources project, and says only "could not log in". The demo permission had to be
   created before either user could authenticate.
2. A tenant filter applies to queries **Servoy builds**. `getDataSetByQuery` with a SQL
   string goes straight to the database and comes back unfiltered, tenant column or not.
   `listMyItems` in the sample uses `QBSelect` for that reason and comes back filtered;
   `countRows` uses a SQL string and does not. The sample keeps both, because the difference is
   not obvious and it is the mistake a tool author will make.

### Five things only running found

1. The SDK resolves its **JSON mapper** and **schema validator** through
   `ServiceLoader`, from `mcp-json-jackson2` - which is not an OSGi bundle. Both are
   supplied explicitly instead, so nothing has to be embedded.
2. **Capabilities are settled at `build()`**, so tools added afterwards leave the
   server advertising none.
3. The **streamable transport needs `startAsync`**, which Servoy's filter chain does
   not support. The stateless transport does not, and fits better anyway - the state
   lives in the pool.
4. `executeMethod` resolves its context as a **form** name first; a scope needs the
   `scopes.` prefix.
5. SDK 2.0.1 refuses any request that does not send
   `Accept: application/json, text/event-stream`, which 1.1.2 accepted. Real MCP
   clients send it; curl has to be told to.

## What remains

**Error markers in Developer** for a tool with an unsupported parameter type. Johan
does not mind if they are missing; dropping the tool with a logged error is what
matters, and that is done.

**Not known:** how a user obtains their token outside a browser. It will be defined in
the cloud and does not exist yet - and it no longer blocks anything here, because the
server does not care what a token looks like. The test authenticator keeps two in a map.

**Still only two users at a time.** The pool is keyed on solution, user and tenants, and
two users have been shown to get their own client and their own tenant. Nothing has been
run concurrently.

## The tests

`servoy-client/servoy_mcp_tests` is a fragment of `servoy_mcp`, packaged `eclipse-test-plugin`, on
the model of `com.servoy.eclipse.model.tests`. Being a fragment is what lets a test reach the
package-private parts - `extractParameters`, `toJsonType`, `quote`, `applyIdentity` - without
widening the API just to be testable.

120 tests over the classes that hold logic rather than plumbing:

| class | what is asserted |
|---|---|
| `McpJsDoc` | what makes a function a tool, and what the agent is told about it |
| `McpToolSchema` | the JSON Schema, and the refusal of anything that is not String, Number or JSON |
| `McpResults` | how a return value is rendered, including the `Double` every number arrives as |
| `McpClientKey` | the key that keeps one user's client away from another's |
| `McpIdentity` | the authenticator is found, the token reaches it untouched, and a refusal is a refusal |
| `McpToolExecutor` | what an authenticated call puts on the session: user, permissions, tenant |
| `McpRuntimePool` | who gets which client, and what invalidating a solution throws away |
| `McpProtocolIntegration` | a real JSON-RPC conversation: `tools/list`, `tools/call`, and every way both refuse |

They need no server, no OSGi and no developer, so they run as an ordinary JUnit test as well as
under Tycho - about a second for the lot.

They split in two by tag. `MCP Unit Tests_mac.launch` runs `@Tag("unit")` - the four classes that
are pure parsing and rendering. `MCP Integration Tests_mac.launch` runs `@Tag("integration")` -
the four that put several pieces together. A tag rather than a package, because a test reaching
`McpRuntime`'s package-private constructor has to live in `com.servoy.mcp`.

Nothing here starts a developer. The classes that reach outside themselves are given what they
reach for, each on a package-private seam that the public path fills in with the real thing:
`McpIdentity.authenticate` takes an `IRepository` and an `IApplicationServer`, `McpRuntime` takes
a `ClientSource`, `McpToolRegistry` takes a `ToolSource`, and `McpSolutionServer` takes an
`Authenticator`. Four lambdas in production, and tests that need no server to exist.

`McpProtocolIntegrationTest` is what the earlier round of integration tests was reaching for and
missing. A JSON-RPC request goes into a real `McpSolutionServer` - the SDK's own transport, the
real catalogue, the real argument mapping, the real rendering - and a JSON-RPC response comes out.
Exactly two things are stood in for: the authenticator module, because no solution is deployed to
hold one, and the client the function runs in, because there is no database behind it. The tools
are not invented either; they are parsed out of `mcp_sample`'s scope files through the same
`McpJsDoc` the scanner uses.

`ClientInfo` is final and cannot be mocked, which turned out to be the better shape anyway: the
executor tests assert what ended up on a real session object rather than which methods were called
on the way there.

Nothing is printed while the tests run. Several of them provoke a failure on purpose, the
production code logs each at error level - correctly, since in a running server that line is the
only notice anyone gets - and a console full of expected errors is where an unexpected one goes
unnoticed. `log4j2-test.xml` silences it, and where the log line is the promise rather than a side
effect, `McpLogCapture` puts one logger back on record so the test can assert it. That matters
most for a tool dropped for an unsupported parameter type: there is no error marker in the
Developer, by design, so that line is the whole of what its author ever hears.

There was an earlier round of integration tests, in a `servoy-eclipse` bundle, that started a real
developer on a scratch workspace and drove the servlet over HTTP. They are gone. Standing a
developer up to check that the executor sets a tenant is expensive to run, slow to diagnose, and
tests the IDE more than it tests the MCP server; the same questions are answered by the fixture
above with a faked authenticator and faked tenants, in a second rather than eighteen.

What that trade gives up is honest to state: nothing now asserts that the bundle resolves in OSGi
with the SDK on its own class path, that `registerWebService` ran, or that `WebServicesServlet`
routes to us. Those are wiring, they fail loudly the first time anyone points a client at the
server, and `mcp_sample` is kept with the tests for exactly that - a manual run against a real
developer when the wiring changes.

`testresources/workspace` is that sample, and it is a whole workspace rather than a solution:
`mcp_sample`, its authenticator module `mcp_sample_auth`, and a `resources` project carrying the
`mcp_user` permission and the `.dbi` that flags `tenant_name` as a Tenant column. All three are
needed - `security.login()` refuses a permission that is not a group in the resources project, and
without the Tenant flag the filter has nothing to act on. Point a developer at it, run
`testresources/create_mcp_tenant_demo.sql`, and the tokens in the table above work.

The solution is deliberately minimal - two scopes and their metadata, no forms and no media -
because one that references a web package stops the developer with a modal dialog asking to
install it. The parsing tests read its scope files directly, so they run against genuine
documentation blocks rather than strings written to suit the parser: if the sample changes, the
tests change with it, which is the point - the sample is what a tool is supposed to look like.

The sample also pins something worth knowing about writing tools: `salesTools_listMyItems` uses
`QBSelect` and comes back filtered by tenant, while `salesTools_countRows` asks with a SQL string
and comes back with every row. A tenant filter applies to queries Servoy builds, not to raw SQL.
It is the mistake someone writing a tool will make.

## Where the code is

| repository | what |
|---|---|
| `servoy-client/servoy_mcp` | the implementation, `com.servoy.mcp`, and the SDK jars it carries |
| `servoy-client/servoy_mcp_tests` | the tests and the `mcp_sample` fixture solution |
| `servoy-client/servoy_shared` | the `MCP Service` solution type |
| `servoy-client/servoy_headless_client` | that type in the headless filter |
| `servoy-client/docs` | this document, next to the code it describes |
| `server/j2db_server` | one line: `registerWebService(...)` in `ApplicationServer.startServices()`, and `invalidateAll()` on import |
| `servoy-eclipse` | the bundle in the feature and in the launch configs, and the save listener |
| `servoy-extensions` | the plugin, now deleted |

Both projects live in `servoy-client`, main and test together. That is where they belong on their
own merits - `servoy_mcp` uses `MCP_SERVICE` from `servoy_shared` and opens clients through
`servoy_headless_client`, both of which are `servoy-client` bundles - and it also removes a real
hazard. Jenkins builds `servoy-client -> server -> servoy-eclipse`, each against the previous
one's *published* artifacts. With the implementation in `server` and the solution type in
`servoy-client`, the first CI run after a change spanning the two failed: the `server` job
compiled against a `servoy_shared` that did not have `MCP_SERVICE` yet. In one reactor the
question does not arise.

### Why its own bundle

The SDK must not become a dependency of the shared build - adding `mcp-core`,
`reactor-core` and `reactive-streams` to `com.servoy.eclipse.target.target` would make
every developer download them, for code most of them never touch. So `servoy_mcp`
carries the three jars on its own `Bundle-ClassPath` and imports nothing from the
platform, exactly as `com.servoy.eclipse.developer.mcp` carries its embedded Tomcat.
The official target is untouched.

The bundle is named `servoy_mcp`, not `j2db_*`: `j2db` is the historical root namespace
and reads like a database. The package is `com.servoy.mcp`, following `com.servoy.base`
rather than nesting under `com.servoy.j2db`.

The coupling to `j2db_server` runs one way only - it imports `com.servoy.mcp` for the
one registration call. Nothing in `servoy_mcp` refers back.

## The sample solution

`mcp_sample` is of type `MCP Service` and carries the `@Tool` functions in two scopes. It ships
with both test bundles, and the parsing tests read its scope files directly, so what the tests
run against and what a person tries by hand cannot drift apart.

`mcp_sample_auth` is its authenticator module: `globals.js` holds a map of two tokens, and
`onOpen(arg, parameters)` reads `parameters.userToken`, calls `security.login()` and
`security.setTenantValue()`. Refusing is simply not calling `security.login()` - the user uid
stays null and the server answers the agent with a refusal.

| token | user | tenant |
|---|---|---|
| `mcp-demo-token-alice` | alice | acme |
| `mcp-demo-token-bob` | bob | globex |

The tenant demonstration needs data to filter: `example_data.mcp_tenant_demo` holds three acme
rows and two globex ones, with `tenant_name` flagged as a Tenant column in its `.dbi`. Whoever
runs the sample by hand creates that table; `testresources/create_mcp_tenant_demo.sql` is the
statement. The permission `mcp_user` has to exist in the resources project, or `security.login()`
refuses - it is in the resources project that ships with the sample.

The solution is deliberately minimal: two scopes and their metadata, no forms and no media. A
solution that references a web package stops the developer with a modal dialog asking to install
it, and a test cannot answer a dialog.
